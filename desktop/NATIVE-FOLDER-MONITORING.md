# Native opt-in indexed-folder monitoring

Open Library → Detailed workspace → Review indexed folders and ingestion records. Each indexed folder shows its current monitor configuration, errors, last polling job and next eligible scan time when enabled. These are refresh-time snapshots, not a live promise about when a scan will finish. Use Refresh index evidence to read the current configuration.

Choose **Review folder monitoring…** to inspect the exact selected path and current monitor revision. A folder without a saved configuration starts Off, with a 300-second interval draft. Enable **Automatically rescan this indexed folder**, choose an integer interval from 60 through 86400 seconds and explicitly press **Save folder monitoring**. Close makes no change. Existing settings initialize the draft as saved. The client does not silently enable monitoring while displaying a folder.

The existing backend polling worker runs only while the local service is running; this feature installs no macOS background agent. Enabling or changing an enabled monitor makes it eligible for a scan immediately. Existing pending polling jobs are not duplicated by the scheduler. Disabling stops future polling but does not cancel an already queued/running scan: use Recent scans → Request cancellation separately. Offline admission errors remain visible and use the backend's existing retry/backoff behavior. Monitoring reads source files and updates app-owned catalog/inbox evidence; it does not copy or edit source audio, tags, cues or external DJ libraries. It does not automatically review inbox records or certify musical suitability.

Settings persist in the existing app database across restart and are part of database backups. Enabled monitors can resume when that workspace's local service starts. Use disposable workspaces and a separate test account on the DJ laptop; never point development at its working Serato library.

The client uses the existing `/api/studio/monitor/save` endpoint, with exactly request_id, dataset_id, root_id, base_revision, enabled and interval_s. It retains the typed exact request in the private native workflow journal before sending, validates the returned request/dataset/root/enabled/revision receipt, and clears recovery only after a verified response is persisted. The receipt does not echo interval_s; the original request binds it and the refreshed snapshot displays the stored interval. A missing or invalid monitor snapshot is an error, not an assumed Off state.

A lost response remains visible across quit/relaunch. **Retry exact folder monitoring** reuses the same request ID and fields; it does not create a replacement save. Only explicit server rejection permits **Discard rejected monitoring**, followed by refresh and a fresh review. Uncertain changes must be reconciled. Pending monitor, inbox and crate operations exclude one another, and backup/workspace-switch guards respect the same pending-operation boundary. Existing journals without the optional monitor field remain readable. Reconcile pending operations before switching to an older checkout.

No folder reassociation, file cleanup, tag repair, full inbox/history pagination or new backend API is introduced. Physical-drive disconnect/reconnect, scheduling under sleep/wake/load, multiple real devices and large libraries still need acceptance. Synthetic checks do not establish those outcomes.
